# Two-Agent Escalation Triage with LangGraph + Ollama

Two agents work in sequence on a Supabase table of customer requests:

1. **Retriever agent:** turns your question into database filters and fetches the matching rows.
2. **Triage agent:** follows a Markdown **skill** (`skills/escalation_triage.md`) to decide
   which requests to escalate, flag VIP customers and suggest next actions.

LangGraph orchestrates the two, and skips the triage step when nothing is found.
Neither agent can change the database: the only tool is read-only.

- **LLM:** Ollama (local, default `qwen2.5:7b`)
- **Orchestration:** LangGraph
- **Agents:** LangChain `create_agent`
- **Database:** Supabase (`enterprise_customer_operations` table)

---

## Architecture

```
        You type a question
        e.g. "Triage the open technical support requests"
                     |
                     v
     +-------------------------------+
     |   AGENT 1: RETRIEVER          |
     |   tool: read_records          |-----> Supabase (read-only)
     |   picks filters from question |<----- matching rows
     +-------------------------------+
                     |
       LangGraph conditional edge (after_retriever)
                     |
        +------------+-------------+
        | rows found               | no rows
        v                          v
  +-----------------------+   +----------------+
  | AGENT 2: TRIAGE       |   | nothing_found  |
  | no tools              |   | "nothing to    |
  | instructions =        |   |  triage"       |
  | skills/               |   +----------------+
  |  escalation_triage.md |           |
  +-----------------------+           |
        |                             |
        v                             v
              Escalation report printed
```

In LangGraph terms:

```
START -> retriever -> (triage | nothing_found) -> END
```

The rows go from Agent 1 to Agent 2 **exactly as the database returned them**
(read from the tool output, not from Agent 1's wording), so Agent 2 never works
from paraphrased data.

### What the skill tells Agent 2

| Level | Rule |
|---|---|
| ESCALATE NOW | priority `critical`, **or** priority `high` and status `open` |
| WATCH | priority `high` and status `in_progress`, **or** contract value ≥ 200,000 |
| NORMAL | everything else (resolved requests are skipped) |
| VIP flag | contract value ≥ 200,000 |

To change the rules or the report format, edit `skills/escalation_triage.md`;
no code changes are needed.

> **Known limitation:** small local models (7B on CPU) format the report well
> but sometimes apply these rules wrongly (e.g. labelling a high+open request
> WATCH). For reliable levels, compute them in Python and let the agent only
> write the report, or use a larger model.

## Project structure

```
supabase_two_agents/
├── app.py                        all the code (settings, tool, agents, graph, chat loop)
├── skills/
│   └── escalation_triage.md      the triage agent's instructions
├── .env                          your settings and keys (never commit this)
├── .env.example                  template for .env
├── requirements.txt
└── .gitignore
```

`app.py` is split into numbered steps:

| Step | What it does |
|---|---|
| 1 | Loads settings from `.env` |
| 2 | Connects to Ollama and Supabase |
| 3 | `read_records` tool (read-only, with filters) |
| 4 | Builds the Retriever agent and the Triage agent (from the skill file) |
| 5 | LangGraph workflow: `retriever_step` → `triage_step` / `nothing_found_step` |
| 6 | Terminal chat loop (`main`) |

## Step 1: Create the table in Supabase

> Already did this for `supabase_multiagent`? Both projects use the same table,
> so skip to Step 2.

1. Sign in at <https://supabase.com/dashboard> and open your project
   (or click **New project** to create one).
2. In the left sidebar click **SQL Editor** → **New query**.
3. Paste the SQL below and click **Run**.

### 1a. Create the table

```sql
-- Table that the agents read
create table if not exists public.enterprise_customer_operations (
    id                  bigint generated by default as identity primary key,
    customer_name       text not null,
    company_name        text,
    email               text unique,
    industry            text,
    service_type        text,
    request_description text,
    priority            text default 'medium',       -- low | medium | high | critical
    assigned_team       text,
    account_status      text default 'active',       -- active | inactive
    resolution_status   text default 'open',         -- open | in_progress | resolved
    contract_value      numeric(12, 2) default 0,
    created_at          timestamptz default now(),
    updated_at          timestamptz default now()
);

-- Keep updated_at current on every UPDATE
create or replace function public.touch_updated_at()
returns trigger
language plpgsql
as $$
begin
    new.updated_at := now();
    return new;
end $$;

drop trigger if exists trg_eco_updated_at on public.enterprise_customer_operations;
create trigger trg_eco_updated_at
    before update on public.enterprise_customer_operations
    for each row execute function public.touch_updated_at();

-- Row Level Security: blocks the public (publishable) key.
-- The app uses the SECRET key, which bypasses RLS.
alter table public.enterprise_customer_operations enable row level security;
```

## Step 2: Get your Supabase URL and secret key

1. In the dashboard go to **Project Settings** (gear icon) → **API Keys**.
2. Copy the **secret key** (starts with `sb_secret_`). Click **Reveal** if hidden.
3. Your **project URL** is `https://<project-ref>.supabase.co`. The project ref
   is the ID in your dashboard address: `supabase.com/dashboard/project/<project-ref>`.

> **Keep the secret key private.** It can read and change every table and
> bypasses Row Level Security. Never commit it, paste it in chat, or use it in
> browser code. If it leaks, roll it on the same API Keys page.

## Step 3: Install and run

Open a terminal (PowerShell on Windows) in this folder.

### 3a. Get the model

```powershell
ollama pull qwen2.5:7b
```

Ollama usually runs in the background after install. If not, run `ollama serve`
in a separate terminal.

### 3b. Create a virtual environment and install packages

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

macOS / Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

### 3c. Configure `.env`

```powershell
copy .env.example .env
```

Edit `.env`:

```env
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_KEY=sb_secret_xxxxxxxxxxxxxxxxxxxxxxxx

SUPABASE_TABLE=enterprise_customer_operations

OLLAMA_MODEL=qwen2.5:7b
OLLAMA_BASE_URL=http://localhost:11434
```

### 3d. Run

```powershell
.venv\Scripts\python.exe app.py
```

(macOS / Linux: `.venv/bin/python app.py`)

Type `exit` to quit.

## Troubleshooting

| Problem | Fix |
|---|---|
| `Please set SUPABASE_URL and SUPABASE_KEY` | `.env` is missing or not in this folder. |
| `[Retriever found 0 record(s)]` for everything | You used the publishable key (RLS blocks it). Use the **secret** key. |
| `Connection refused` on port 11434 | Ollama isn't running. Start it with `ollama serve`. |
| `model "qwen2.5:7b" not found` | Run `ollama pull qwen2.5:7b`. |
| Replies take many minutes | The model is running on CPU (one question made two LLM agents run). Close other apps, or set `OLLAMA_MODEL=llama3.2` in `.env` (faster, less accurate). |
| Wrong escalation levels | See *Known limitation* above. |
